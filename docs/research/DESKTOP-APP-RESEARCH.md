## A1. Local sandboxing model

| Item | Status | Detail |
|---|---|---|
| Sandbox is OS-enforced, per-platform | CONFIRMED ([sandboxing](https://learn.chatgpt.com/docs/sandboxing)) | macOS = Seatbelt via `sandbox-exec -p`; Linux/WSL2 = **bubblewrap** (`bwrap` on PATH, else bundled helper needing unprivileged user namespaces; warns at startup if missing); Windows = native sandbox (restricted tokens + ACLs), WSL2 uses the Linux impl. Ubuntu AppArmor `bwrap-userns-restrict` notes included. |
| Sandbox covers spawned commands | CONFIRMED ([sandboxing](https://learn.chatgpt.com/docs/sandboxing)) | "The sandbox applies to spawned commands, not just to built-in file operations… `git`, package managers, test runners inherit the same sandbox boundaries." |
| Sandbox modes | CONFIRMED ([sandboxing](https://learn.chatgpt.com/docs/sandboxing)) | `read-only` (inspect only), `workspace-write` (**default**, read+edit inside workspace+run routine commands), `danger-full-access` (no sandbox, no filesystem/network boundary). |
| Approval policies | CONFIRMED ([sandboxing](https://learn.chatgpt.com/docs/sandboxing), [agent-approvals-security](https://learn.chatgpt.com/docs/agent-approvals-security)) | `on-request` (default) and `never`. `untrusted` is **retired**; migrate to `on-request`. Full access = `danger-full-access` + `never`. |
| Desktop UI wording of the 3 modes | CONFIRMED ([sandboxing](https://learn.chatgpt.com/docs/sandboxing), [permission-modes](https://learn.chatgpt.com/docs/permission-modes)) | Permissions control **beneath the composer**; menu can include **Ask for approval**, **Approve for me**, **Full access**, and named/custom permission profiles. "For most work, start with **Ask for approval**." |
| "Approve for me" = auto-review | CONFIRMED ([permission-modes](https://learn.chatgpt.com/docs/permission-modes), [auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)) | Sends *eligible* approval requests to a reviewer agent (`approvals_reviewer = "auto_review"`). "Changing who reviews a request doesn't expand the sandbox." Reviewer states: **Reviewing, Approved, Denied, Aborted, Timed out**. `/approve` re-opens a denied retry. |
| Permission profiles (beta) | CONFIRMED ([permissions](https://learn.chatgpt.com/docs/permissions)) | Built-ins `:read-only`, `:workspace`, `:danger-full-access`; custom `[permissions.<name>]` with `workspace_roots` + filesystem rules. |
| Rules (per-command allow/prompt/forbid) | CONFIRMED ([rules](https://learn.chatgpt.com/docs/agent-configuration/rules)) | Allow/prompt/forbid command prefixes outside the sandbox — "often a better fit than broadly expanding access." |
| **Approval prompt wire format** | CONFIRMED ([app-server](https://learn.chatgpt.com/docs/app-server)) | Server→client JSON-RPC requests the client must render:<br>• `item/commandExecution/requestApproval` — `itemId`, `threadId`, `turnId`, optional `reason`, `command`, `cwd`, `commandActions`, `proposedExecpolicyAmendment`, `networkApprovalContext`, `availableDecisions`.<br>• `item/fileChange/requestApproval` — optional `reason`, `grantRoot`.<br>• `item/permissions/requestApproval` — `environmentId`, `cwd`, `reason`, requested network/filesystem perms; respond with the granted **subset**; `scope: "session" \| "turn"`.<br>• `mcpServer/elicitation/request` — `mode: "form" \| "openai/form" \| "url"`.<br>• App/connector tool approvals → options **Accept / Decline / Cancel**.<br>**Decision vocabulary:** `accept`, `acceptForSession`, `decline`, `cancel`, `acceptWithExecpolicyAmendment`. |
| Approval prompt grouping | CONFIRMED ([app-server](https://learn.chatgpt.com/docs/app-server)) | Concurrent **network** approvals are grouped by `(host, protocol, port)` so one prompt can unblock several. "Clients should render a network-specific prompt and not rely on `command` being a user-meaningful shell-command preview." |
| Approval flow UI order | CONFIRMED ([app-server](https://learn.chatgpt.com/docs/app-server)) | `item/started` (pending item with command/cwd) → `requestApproval` → client decision → `serverRequest/resolved` → `item/completed` with `status: completed | failed | declined`. |
| Thread state flag for approvals | CONFIRMED ([app-server](https://learn.chatgpt.com/docs/app-server)) | `status: { "type": "active", "activeFlags": ["waitingOnApproval"] }` — the thing to badge in a task list. |
| Keyboard approve/decline | CONFIRMED ([commands](https://learn.chatgpt.com/docs/reference/commands)) | **Enter = Approve request**, **Esc = Decline request** when an approval request is open. |
| Computer Use app approvals | CONFIRMED ([computer-use](https://learn.chatgpt.com/docs/computer-use)) | Per-app approval dialog; **Always allow** persists the app in Settings → Computer Use → Always allow. Windows persistent list `computer_use.windows.always_allowed_app_ids`. |
| Browser website permissions | CONFIRMED ([browser](https://learn.chatgpt.com/docs/browser)) | Per-site: **Always ask** / **Auto approve** / **Always allow**; per-site overrides; per-site permissions can be **Requires approval / Always allow / Block** (Settings → Browser → Agent permissions). |
| Sandbox ⊥ approvals | CONFIRMED ([sandboxing](https://learn.chatgpt.com/docs/sandboxing)) | "Sandboxing and approvals are different controls that work together. The sandbox defines technical boundaries. The approval policy decides when the agent must stop and ask." |

| "Hand off" Local ⇄ Worktree | CONFIRMED ([git-worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)) | Moves chat **and** code; Codex performs the Git ops because a branch can only be checked out in one place at a time. `.worktreeinclude` carries gitignored files into the worktree. |
| Steering vs queuing | CONFIRMED ([prompting](https://learn.chatgpt.com/docs/prompting)) | While Codex works: **Steer** (adds to the current run) or **Queue** (saves for the next run). | "Review checkpoints" | PARTLY / NOT FOUND as a UI control | "Create Git checkpoints before and after a task so you can revert changes" appears as *advice* in the CLI and IDE quickstarts ([cli](https://learn.chatgpt.com/docs/codex/cli), [ide](https://learn.chatgpt.com/docs/codex/ide)). No dedicated Codex-desktop "checkpoint" widget was found. |
| "Background tasks" pane | NOT FOUND for Codex | Codex docs describe a Background-tasks pane only for Claude Code. Codex's equivalents are the **Activity view**, cloud tasks, and the floating pet. |
| Cloud task semantics | CONFIRMED ([environments/modes](https://learn.chatgpt.com/docs/environments/modes)) | Each cloud task has its own working files; local files, processes, browser sign-ins and VPN are not transferred; task must be started against a published environment you can access. |

# C. Highest-value items to copy into a GTK4 Linux client

1. **Two-axis permission model, clearly named.** Codex: *Ask for approval / Approve for me / Full access* + a separate sandbox concept. Claude: *Manual / Accept edits / Plan / Auto / Bypass permissions* + a separate sandbox concept. Both put the selector **under the composer**, and both state that switching reviewer does **not** widen the sandbox.
2. **Approval prompt decision vocabulary.** Codex (from the app-server contract): `accept`, `acceptForSession`, `decline`, `cancel`, plus an execpolicy amendment. Claude: *Allow once / Allow for this session / Allow for this task / Always allow / Deny*. A GTK client should render at minimum: **Allow once / Always allow this session / Always allow this project / Deny**, with an explicit "network access to host:port" variant (Codex groups by host+protocol+port).
3. **Keyboard-first approvals**: Enter = approve, Esc = decline (Codex). Claude fixed a bug where "stacked permission prompts slid up under the mouse pointer right after one is answered" — a GTK4 client should render approval cards **in a non-modal, stacking queue** anchored away from the pointer, and ignore a send keystroke aimed at the message box.
4. **A visible "waiting on you" state.** Codex: `activeFlags: ["waitingOnApproval"]` + Activity view (unread / running / waiting for your response) + "Next chat needing attention" shortcut. Claude: "needs-input marker" on the sidebar row + OS notification when a session finishes.
5. **Scoped escalation, not blanket access.** Codex's `grantRoot` on file-change approvals, `scope: session|turn` on permission grants, `proposedExecpolicyAmendment` on command approvals, and "choose the narrowest scope that lets the task continue" — plus named permission profiles (`:read-only`, `:workspace`, `:danger-full-access`).
6. **Rules instead of blanket exceptions**: per-command allow/prompt/forbid prefixes (Codex rules) and org tool policies (Claude "Restrict to Ask" / "Blocked").
7. **Review pane driven by Git state**, not by the agent's own claims — with scopes Unstaged / Staged / Commit / Branch / **Last turn**; inline comments on lines; stage/unstage/revert at diff/file/hunk level.
8. **Worktree isolation + Handoff** as the default way to run parallel agents on one repo, with a "create branch here" escape hatch and a "hand off to my checkout" button.
9. **Steer vs Queue**: the message you send while the agent works can either redirect the current run or be held for the next one, with a default in Settings and queued messages shown **above the composer** where they can be edited/reordered/deleted.
10. **Pane-based workspace** (Claude) rather than a single scrolling transcript: chat / diff / browser / terminal / file / plan / tasks, draggable, resizable, poppable into their own window, with an overflow **⋮** menu for panes that have no title-bar button.
11. **Session details rail** as a set of small cards (Environment, Changes, Context %, Running) rather than a settings dialog.
12. **Usage surfaces**: a plan-usage ring next to the model picker + a context-usage card with a per-category breakdown + `/status` showing rate limits, and `/usage` opening billing.
13. **Global hotkey + quick entry** (Claude): a hotkey summons a small always-on-top composer; screenshot/window-share attach; a second hotkey for push-to-talk dictation. On Linux: X11 + the GlobalShortcuts portal for Wayland.
14. **Status-indicator vocabulary** worth reusing verbatim: Codex Micro's *Idle / Thinking / Complete / Requires input / Error* colour set; Codex pets' *Running / Needs input / Ready / Blocked*; Claude app permissions' *View only / Click only / Full control* tiers.
15. **MCP as two distinct install paths**: a GUI extension directory (one-click `.mcpb`, built-in Node runtime, `sensitive: true` → OS keyring) for local servers, and URL-based remote connectors with a transport selector (http / sse / ws) and per-tool "Blocked". Show connection status and tool lists inside the chat's **+** menu.
16. **Scheduled tasks** with a Local/Cloud split and an explicit "Only on this computer" switch, one-time vs recurring, and a minimum-interval rule.
17. **Natural-language scheduling**: "remind me at 3pm tomorrow to check the deploy" → a one-time task that disables itself after firing.
